A selected seat is not a reservation

Where the Queue prototype ends and database correctness begins.

Danny Perojevic · October 13, 2026· Updated October 15, 2026

A17 is selected. Who owns it?

The Queue frontend lets me select A17, see its price, and continue into a checkout countdown. That makes the customer flow tangible. It does not mean the system has reserved A17. Right now, the prototype uses mock inventory and simulated checkout.

Two browsers can disagree

Another browser can select the same seat. Neither browser can settle ownership using its own state. The backend needs a transaction that checks and changes the authoritative inventory together. A stale page should get a clear failure rather than an order for a seat someone else already booked.

The backend experiment I want to run

The next slice is Spring Boot and PostgreSQL. I want two requests to compete for A17, then compare row locking, optimistic locking, and an atomic conditional update against the same test. The first question is whether at most one booking succeeds. Latency is useful after that passes.

Keep the prototype useful

Building the frontend first exposed questions the API will need to answer: when does a hold begin, when does it expire, and what happens if confirmation is retried? Redis and Kafka remain possible later additions. The reservation boundary needs to work before I have a reason to add them.
