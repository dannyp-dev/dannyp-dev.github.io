Concurrent Ticketing Platform

A full-stack ticketing platform in development, connecting event discovery, seat availability, and reservations through a shared booking workflow.

In development · Sep 2026

The question

How do you keep seat reservations fast without allowing two customers to purchase the same seat?

The approach

The current Next.js prototype models the customer journey with mock data. The planned backend is a Spring Boot REST API with PostgreSQL as the authority for events, seats, and reservations. Redis and Kafka will be evaluated after reservation correctness and concurrency behavior are established.

Current progress

The customer-facing prototype covers event discovery, interactive seat selection, simulated checkout, and confirmation. Event and seat data is currently mocked. Authoritative holds, reservation transactions, and concurrency experiments are the next milestones.

Key decisions

  • Connect the Next.js interface to a Spring Boot REST API.
  • Model events, seats, and reservations in PostgreSQL to support data integrity.
  • Develop Redis availability and Kafka processing without claiming unvalidated performance.

Technology boundary

The current frontend uses Next.js, React, TypeScript, and native CSS. Spring Boot and PostgreSQL are the next backend slice. Redis and Kafka remain possible future additions.

Start with the complete customer journey.

I built the frontend first so the reservation API would answer real interface needs, rather than an abstract list of endpoints. The prototype connects discovery, event details, seat selection, checkout, and a mobile-ticket-style confirmation.

Four mock events and 180-seat maps make the flow concrete. Seats have available, held, sold, and selected visual states; selection is limited to six seats. A seven-minute checkout countdown and itemized pricing make the edge cases visible before backend integration.

These are presentation states, not real inventory guarantees. Checkout is simulated, and browser state cannot prevent two different users from selecting the same seat.

Correctness belongs in the database.

The next backend slice will connect the Next.js interface to a Spring Boot REST service and PostgreSQL. The first design decision is the relationship between Event, Seat, Reservation, and Order, including whether venue inventory should be reusable.

The browser can suggest that a seat is available, but the server must make the final decision inside a transaction. I want to reproduce two requests racing for seat A17, then compare row locks, optimistic locking, and atomic conditional updates against the same correctness test.

  • Keep database state authoritative when the interface is stale.
  • Define hold expiration and confirmation at the transaction boundary.
  • Evaluate idempotency so repeated requests cannot create duplicate orders.

Prove the small system before scaling it.

The roadmap prioritizes a correct reservation flow before adding infrastructure. These are planned milestones, not completed capabilities.

  • Agree on the domain model and scaffold the smallest Spring Boot/PostgreSQL slice.
  • Integrate real holds, expiry, and confirmation into the existing customer journey.
  • Run concurrent booking tests, compare locking strategies, and document failures as well as successes.
  • Measure latency and throughput only after correctness passes.
  • Evaluate Redis for availability reads and Kafka for event processing when measured requirements justify them.
  • Publish a bounded demo using synthetic events, with no real payments or customer information.
