Simulated Workflow Engine

A concurrent task engine that schedules asynchronous work across distributed workers and recovers jobs when a worker disappears.

Completed project · Jul 2026

The question

How can asynchronous work keep moving when workers fail in the middle of a job?

The approach

The engine schedules tasks in Go and distributes them through Redis Streams consumer groups. Retry and reclamation logic recovers abandoned work, PostgreSQL preserves task state, and gRPC coordinates worker activity.

The result

The system recovered 99.9% of jobs after simulated worker failures while sustaining sub-millisecond scheduling under concurrent load.

Key decisions

  • Treat every claimed task as recoverable until completion is recorded.
  • Use consumer groups to distribute work while tracking pending deliveries.
  • Separate durable task state from fast worker coordination and queue operations.

Technology

Go / PostgreSQL / Redis Streams / gRPC / Docker

Separate work from the worker running it.

This project explores a deceptively simple problem: scheduling a task is easy, but keeping it alive when its worker disappears is not. The engine uses Go to coordinate asynchronous execution across worker processes, rather than tying a job’s lifetime to one process.

PostgreSQL records task state, Redis Streams distributes work through consumer groups, and gRPC provides worker coordination. Docker makes the multi-process environment reproducible for simulated failure scenarios.

Claimed does not mean completed.

Consumer groups track delivery and pending work. Retry and reclamation logic allow abandoned tasks to become executable again after a worker failure. The important distinction is between receiving a job and recording that it has finished.

Recovery also creates a tradeoff: a retry may repeat work. Reclamation is not evidence of exactly-once execution. Durable task state and clear completion boundaries are important when reasoning about failures and side effects.

  • Redis Streams handles delivery and pending work.
  • PostgreSQL preserves task state beyond a worker’s lifetime.
  • gRPC separates coordination from durable storage.
  • Retries and reclamation recover work instead of silently losing it.

Failure is part of the workload.

The completed engine recovered 99.9% of jobs after simulated worker failures and sustained sub-millisecond scheduling under concurrent load. These are the results reported in my resume, not a production uptime guarantee or end-to-end task latency claim.

The value of the project is the recovery path: what happens to pending work when execution stops unexpectedly. A public demonstration should make that path visible through synthetic tasks and a controlled worker interruption, without exposing unrestricted backend access.
